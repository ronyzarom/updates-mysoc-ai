# Fresh host in one command (normal server or DR) — 1‑2‑3

A brand-new mysoc server stands itself up from a single admin command. A normal
server and a DR server install **identically**; DR differs only by one extra
click in step 3 (choosing primary/standby in the dashboard). No frictions, no
per-host runbook.

## 1 — Start a clean VM

- Ubuntu LTS, outbound HTTPS to `updates.mysoc.ai`.
- DNS for your `<fqdn>` points at the VM; ports 80 and 443 reachable (port 80 is
  only needed if you use `--tls letsencrypt`).
- Have your **platform license key** (dashboard → Operators) and, for a wildcard
  cert, the `fullchain.pem` / `privkey.pem` on the box.

## 2 — Run the one command

Wildcard certificate:

```bash
curl -fsSL https://updates.mysoc.ai/install/mysoc-enroll.sh | sudo bash -s -- \
  --license-key <KEY> --domain <fqdn> \
  --tls wildcard --cert /path/fullchain.pem --key /path/privkey.pem
```

Let's Encrypt instead:

```bash
curl -fsSL https://updates.mysoc.ai/install/mysoc-enroll.sh | sudo bash -s -- \
  --license-key <KEY> --domain <fqdn> --tls letsencrypt --email ops@<fqdn>
```

That is the whole install. It ends with:

```
[mysoc-enroll] DONE  https://<fqdn>  version=<x.y.z.b>
```

The **same command works for a DR server** — you do not install DR differently.

## 3 — Open the site and create the first administrator

Open `https://<fqdn>`. On a brand-new install the empty database has no users
yet, so the login page detects it (`GET /api/v1/auth/setup-status`) and takes
you straight to `https://<fqdn>/setup`:

- create the **first administrator** (name, email, password against the live
  policy checklist), then sign in.

No SSH or extra step — this happens in the browser. `/setup` is where the admin
is born: no password ever passes through the install seed, and once any user
exists the endpoint is inert (409). `ADMIN_EMAIL` from the seed is not
pre-created as a user.

**DR only:** after signing in, go to **Settings → Disaster Recovery** and set
this box as **Primary** (or **Standby**, pointed at the primary). A normal
server is finished at this step.

### What the one command does

The `mysoc-enroll.sh` bootstrap is deliberately thin — it does only what the
host cannot do for itself, then hands the whole bring-up to the cascade:

1. ensures `rsync` + `curl` exist,
2. fetches and **checksum-verifies** the updater kit from
   `https://updates.mysoc.ai/install/`,
3. writes the install seed `/etc/mysoc/install-seed.env` (0600 root:root),
4. installs and enrols the updater (`install.sh --clean --executor filesystem`,
   real mode, `current_version 0.0.0`),
5. starts the updater and waits for `/health`.

Everything else — PostgreSQL, nginx, Node, the service user, the database and
app role, the `.env` **secrets (generated on the host, never in the seed)**, TLS,
the systemd units, the baseline schema, and the application code — is installed
by the artifact's `first_install` phase, through the exact same cascade path
every later upgrade uses. See
[`UPDATE-ENTRYPOINT-CONTRACT.md`](UPDATE-ENTRYPOINT-CONTRACT.md) for the phase.

## Options

| Flag | Meaning |
| ---- | ------- |
| `--license-key` | platform license key (required) |
| `--domain` | public FQDN (required; also the default instance id) |
| `--tls wildcard --cert … --key …` | use an existing wildcard cert |
| `--tls letsencrypt --email …` | obtain a Let's Encrypt cert |
| `--instance-id` | override the instance id (defaults to the domain) |
| `--smtp-host/-port/-user/-pass/-from` | seed outbound email |
| `--admin-email` | first admin account |
| `--siemcore-url` | pin a siemcore relay URL |
| `--seed-file <path>` | preset any of the above as defaults; flags still override |

The seed file uses the artifact's key names (`DOMAIN`, `TLS_CERT_PATH`,
`TLS_KEY_PATH`, `SMTP_USERNAME`, `SMTP_PASSWORD`, …); explicit flags win over
seed values. Secrets (`JWT_SECRET`, `ENCRYPTION_KEY`, `DB_PASSWORD`) are
generated by the artifact into `/opt/mysoc/backend/.env` — never put them in the
seed.

## If it is not healthy yet

`first_install` starts with a **read-only preflight** and mutates nothing until
it passes. If a prerequisite is wrong (seed incomplete, DNS/ports, TLS material,
PostgreSQL not clean, disk), the updater **refuses, reports the one-line reason,
and backs off** (5m → 15m → 60m) instead of thrashing. The bootstrap prints the
recent log and the fix. Correct the prerequisite and the updater **resumes
automatically** on the next cycle (or `sudo systemctl restart mysoc-updater` to
retry now). Because `first_install` is idempotent and resumable, re-runs
continue rather than start over.

```bash
journalctl -u mysoc-updater -f        # watch progress / preflight verdicts
curl -fsS http://127.0.0.1:8080/health
```

## Why install ring

The one command lands the host on the current **stable** release, which is what
a production normal/DR server wants. To put a fresh host on a non-stable ring
(e.g. the alpha DR lab), enrol observe-first and set the ring before any install
runs — see "Observe-first" in [`../kits/mysoc/README.md`](../kits/mysoc/README.md).
