# Isolated pod coordinated update contract (candidate)

Status: proposed product integration, not deployed or HA-qualified. Owner: Updates transport, verification, serial delivery and reporting; SiemCore authority, maintenance, lifecycle, health and compensation. The rejected SSH observer exception must not be executed.

The existing 1.16.1.23 updater and installed root hook independently verify the signed universal product archive then invoke its `updater/apply` with apply, health or rollback. The hook privately extracts the authenticated bundle and gives the product root execution with a clean environment. Each invocation is bounded to 810 seconds. No new root trust, arbitrary command endpoint, component version fiction, or SSH software update is needed.

SiemCore apply owns the complete transition: acquire durable maintenance against observed ownership, drain the active data plane, keep B's database/Redis replication alive, stage role software and observer, and use a protected intent binding designated A, previous generation, operation, and target version. A's new controller must atomically compare the exact maintenance marker and intent with owner absence, then delete maintenance and put the leased A owner in one transaction. Fresh authenticated peer-standby proof, watchdog, promotion, start, and traffic verification are mandatory. Ordinary unplanned takeover keeps fencing. Never remove initialized state or weaken Redis's required replica.

Delivery qualification order is A, B, witness. Before publication on the normal isolated application channel, snapshot the three exact instance IDs' flags and groups, disable automatic application on all three through the existing API, and verify readback plus absence of an in-flight apply. Enable only the intended role. Wait for successful target version reporting AND independent owner, replication, observer, and public health evidence, disable it before enabling the next role. Abort on unexpected identity or flag drift. Restore exact original flags only when the intended operation is complete or safe recovery has been verified. Never alter other fleet assignments or release targets. A published isolated observer-channel candidate remains ineligible for normal application delivery.

A is first because the old controller cannot safely resume maintenance without fencing B. Product role B apply later requests maintenance/resume through quorum, using the already updated A controller. Witness is last and must retain two healthy quorum voters. Role-specific product checks must prove this order before live rollout.

Success means the application and role health match the offered version; staging or a running observer alone is insufficient. The updater persists a whole-product version only after apply and health succeed. No SiemCore .31 success report may describe an application still on .30.

Rollback boundary: filesystem rollback restores the old application `current` link BEFORE calling rollback. Thus old .30 entrypoint executes, not the failed candidate's rollback code. New maintenance recovery code must live in a product-owned durable location outside the application link, and the candidate must compensate before returning failure or retain a clearly failed-closed state recoverable through the supported product flow. Do not claim automatic rollback until interruption, apply/health timeout, rollback failure and retry are qualified. No DB backup/restore or migration rollback.

Local Updates tests exercise real filesystem phase delegation and restored-entrypoint ordering, signed pipeline failure reports, and a real subprocess health timeout without installed-version advancement. These are protocol regression tests, not a live pod or DR acceptance result.
