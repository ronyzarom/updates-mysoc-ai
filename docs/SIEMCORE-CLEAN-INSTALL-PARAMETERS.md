# SiemCore clean-install parameters

Source contract checked 2026-09-17 against `kits/siemcore/install.sh`,
`greenfield-bootstrap.py`, `installation-type.py`, and SiemCore's
`deploy/cluster/updater/greenfield.py`. This guide describes current source inputs,
not confirmation that a published kit or every POD lifecycle is qualified.
Observer update fixture acceptance does not qualify clean Observer installation.

## Before starting

Use `--clean` only for an empty host. It enrolls the product at version `0.0.0`.
Automatic product provisioning also requires `--greenfield-input`; `--clean`
alone does not supply the application settings. Do not use it to upgrade an
existing server or restore a production database.

Prepare a separate root-owned, mode `0600` input file for each host under a
root-owned protected directory, for example `/root/provisioning/pod-a.json`.
Do not include customer secrets in downloadable kits, source control or logs.
The input has exactly two top-level objects: `application` and `release`.
Credentials and certificates must be real provisioned values; placeholders below
are explanatory and are not runnable configuration.

Linux/systemd, root access, Python >=3.9, OpenSSL with Ed25519 support,
sudo/visudo, coreutils and useradd are kit prerequisites. Product dependencies
are owned by the signed SiemCore provisioning logic. Missing dependencies are
not permission to fetch arbitrary public packages or images.

## Installer command-line parameters

| Parameter | Required / default | Meaning |
| --- | --- | --- |
| `--clean` | Required for fresh installation | Select fresh-host enrollment. |
| `--greenfield-input FILE` | Required for automatic application bootstrap | Protected JSON described below. |
| `--instance-id ID` | Required | Unique, stable updater identity for this machine; matches `application.updater_instance_id` (or fallback `application.instance_id`). |
| `--parent-url URL` | Required | MySoc relay child endpoint, including port, e.g. `https://relay.example:18443`. |
| `--parent-id ID` | Required | Enrolled MySoc parent instance ID. |
| `--customer-id ID` | Required | Customer fleet grouping identity. |
| `--customer-name NAME` | Required | Customer display name. |
| `--license-key KEY` | Required | Updater enrollment credential; distinct from the application MySoc API key. |
| `--signing-key HEX` | Required | Trusted release Ed25519 public key, 64 hex characters; must match `release.public_key`. |
| `--server-type TYPE` | Can derive from JSON | `normal`, `pod-active`, `pod-stby`, `pod-observer`. Explicit choice must agree with topology. |
| `--pod-id ID` | POD; can derive | Matches `application.cluster_id`; omit for Normal. |
| `--node-id ID` | POD; can derive | `1` for A, `2` for B, `witness` for Observer; omit for Normal. |
| `--self-update-channel stable` | Default `stable` | Updater channel, independent of product release channel and fleet ring. |
| `--ca-file FILE` | Conditional | Parent relay private CA; omit for publicly trusted TLS. |
| `--relay-cert-file FILE` | Optional, paired | Existing child-facing relay certificate chain. |
| `--relay-key-file FILE` | Required with relay certificate | Matching private key. |

Missing required enrollment values are prompted on an interactive terminal;
unattended runs must supply them. Current source is not a URL-only installer.
`--current-version` belongs to `--update`, not clean installation.

Testing uses updater channel `stable`, central fleet group `alpha`, and automatic
signed self-updates. There is no `--alpha` flag here: assign and verify the ring
in Fleet separately. Preserve explicit holds. A product channel in the release
receipt does not change the updater self-update channel.

## Application parameters by role

R = required input; G = generated by installer; — = omit/not required.
A and B are immutable machine identities, not permanent processing assignments.
An Active label never grants processing permission; both data nodes bootstrap
paused until qualified Observer authority permits processing.

| JSON field under `application` | Normal | POD A | POD B | Observer | Meaning |
| --- | --- | --- | --- | --- | --- |
| `schema` | `1` | `2` | `2` | `2` | Input schema. |
| `topology` | `single` | `pod` | `pod` | `pod` | Installation topology. |
| `pod_role` | — | `a` | `b` | `witness` | Bootstrap node identity. |
| `cluster_id` | R | R | R | R | Cluster identity; same POD ID across its three hosts. |
| `instance_id` | R | R | R | — | Logical MySoc application identity; shared by A/B. |
| `updater_instance_id` | Recommended | R* | R* | R | Unique enrolled machine identity, matching CLI `--instance-id`. |
| `database_name` | R | R | R | — | Application database name. |
| `machine_id` | G | G | G | G | Written from local `/etc/machine-id`; not copied from another host. |
| `frontend_url` | R | R | R | — | HTTPS application endpoint. |
| `mysoc_url` | R | R | R | — | HTTPS MySoc application endpoint, distinct from relay URL. |
| `admin_email` | R | R | R | — | Initial administrator identity; B validates it but skips initial account bootstrap. |
| `mysoc_api_key` | R | R | Omit | Omit | MySoc application bootstrap credential; rejected on B/Observer when nonempty. |
| `nodes` | — | R | R | R | Object with exactly `a`, `b`, `witness`, each a distinct routable IPv4 address. |
| `quorum_credentials` | — | R | R | R | Per-host PEM trust material; detailed below. |
| `traffic_verify_url` | — | R | R | — | HTTP(S) URL whose path is `/__lb_whoami`, no userinfo/query/fragment. |
| `shared_secrets` | — | R | R | — | Shared A/B application/database secrets; detailed below. |
| `pod_agent` | — | R | R | — | Per-node peer authentication material. |
| `peer_fencing` | — | R | R | — | Exact GCP identity of the peer machine. |
| `redis_auth` | — | — | — | R | Witness Redis authentication, 64 lowercase hex characters. |
| `processing_mode` | Omit | Optional | Optional | Omit | Current optional value `supervised-v1`; do not treat it as lifecycle readiness or enable it without qualification. |

\* The parser can fall back to `instance_id`, but using that fallback on both A/B
would duplicate updater identities. Always supply explicit distinct updater IDs
for POD machines. Identity strings use letters/digits, `_` and `-`, start with a
letter/digit, and have at most 101 characters.

`frontend_url` and `mysoc_url` require HTTPS, a hostname, no userinfo/query/fragment,
and an empty or `/` path. They do not themselves provision DNS or TLS certificates.

### POD credential structures

| Object | Exact fields / constraints |
| --- | --- |
| `quorum_credentials` on every POD host | `server_crt`, `server_key`, `peer_crt`, `peer_key`, `client_ca_crt`, `peer_ca_crt`, `node_crt`, `node_key`, `updater_crt`, `updater_key`. PEM strings, maximum 16 KiB each. |
| Additional `quorum_credentials` on A only | `root_crt`, `root_key`. Current bootstrap schema requires these on A; do not distribute them to B or Observer. |
| `shared_secrets` on A/B | Exactly `pg_super`, `pg_repl`, `pg_app`, `redis`, `jwt`, `admin`; each a provisioned 64-character lowercase hex string. Both nodes use matching shared values. |
| `pod_agent` on A/B | `ca_crt`, `cert`, `key` (PEM); `peer_certificate_sha256`, `incoming_token`, `outgoing_token` (64 lowercase hex characters). Provision matching peer trust and directional tokens. |
| `peer_fencing` on A/B | Exactly `provider: "gcp"`, `project`, `zone`, `name`, `id`; identify the peer VM, including its immutable numeric GCP ID. Names use lowercase GCP-style identifiers; ID is 1–20 decimal digits, starting nonzero. |

For Normal, bootstrap generates and retains database, replication, Redis, JWT
and initial administrator secrets locally. For POD A/B, provisioning must supply
shared values before installation; do not independently generate incompatible
credentials on each machine. The Observer does not receive application database,
LLM or archive credentials. The current legacy witness schema still requires
`redis_auth`; this does not mean the new Observer lifecycle is fully qualified.

## First signed release (`release` object)

| Field | Required value |
| --- | --- |
| `version` | Four-part numeric product version, e.g. `3.3.152.36` (illustration only, not an approved target). |
| `sha256` | Exact artifact digest, 64 lowercase hex characters. |
| `public_key` | Trusted Ed25519 public key, 64 lowercase hex characters, matching CLI signing pin. |
| `signature` | Base64-encoded 64-byte signature from the approved release receipt. |
| `channel` | Explicit product channel; lowercase letter followed by up to 19 lowercase letters, digits or hyphens. |

Obtain these together from an approved signed release. Do not invent a checksum,
signature, channel or target version. These inputs do not publish/promote a release
or bypass prerequisite/role checks.

## LLM and archive initial settings: legacy path and schema 3

The following application installer options exist, but the legacy schema 1/2
cascade path does not forward them. Schema 3 GCS source integration is described
in the next section; LLM setup remains separate. Adding arbitrary fields to the JSON will
not configure these services. Configure them through the product-supported setup
path until the provisioning contract is extended and qualified.

| Feature | Settings to collect | Current destination / support |
| --- | --- | --- |
| AI providers (optional) | Provider, model choice and provider API key; leave paid AI disabled unless requested. | SiemCore Settings → AI Providers; `llm_config` database table. Underlying installer accepts `--llm-openai-key`, `--llm-anthropic-key`, `--llm-google-key`, `--llm-primary`; these are not updater `install.sh` flags. |
| Archive destination | Backend (`local`, `gcs`, `s3`, `azure_blob`), bucket/container, region, storage class, retention. | Underlying application installer has archive flags; runtime archive policies/settings are product-owned. Schema 3 introduces explicit GCS retention below. |
| GCP Coldline | GCP project, bucket or bucket-provisioning policy, location, `COLDLINE`, retention days, authentication method. | Runtime settings include `GCP_PROJECT_ID`, `TIERED_GCS_BUCKET`, `GCP_BUCKET_LOCATION`, `TIERED_STORAGE_CLASS`, `TIERED_DEFAULT_RETENTION_DAYS`, `TIERED_AUTO_PROVISION_BUCKET`. Not forwarded on the legacy schema 1/2 path. |
| GCP authentication | VM workload identity/default credentials, or a provisioned service-account credential file. | File mode uses `GOOGLE_APPLICATION_CREDENTIALS`; documented deployment path `/etc/siemcore/gcp-archiver.json`, made available to the archiver through a protected read-only mount. Do not bundle the key. |

A/B must both have the required runtime access before failover is qualified.
Do not assume database synchronization distributes host files or cloud IAM access.
Missing archive setup must not be represented as a successful Coldline installation.

## Schema 3 extension under integration review

The product team has added source support for the following contract. The Updates
kit source now accepts schema 3 and preserves its feature objects for product
validation. Do not use schema 3 with a published kit until the kit, outer apply
hook and signed product executor all support it. The outer hook must classify schema 3 POD inputs as POD, never Normal.
Older product executors reject schema 3 rather than silently ignoring new settings.
This section is an integration reference, not a qualified installation procedure.

Use `application.schema: 3` with `topology: single` or `pod` and one of the
following explicit feature objects. Existing schema 1/2 inputs remain unchanged;
new feature fields on old schemas are rejected by the new product validator.

### `application.archive` (Normal or POD data nodes)

All fields are required; unknown keys are rejected by the product validator.

| Field | Value |
| --- | --- |
| `backend` | `gcs` |
| `project_id` | GCP project ID. |
| `bucket` | Bucket name accepted by product validation. |
| `location` | Lowercase location, for example `me-west1`. |
| `storage_class` | `STANDARD`, `NEARLINE`, `COLDLINE`, or `ARCHIVE`. |
| `retention_days` | Integer 1–36500; booleans are invalid. |
| `auto_provision` | Boolean. |
| `authentication` | Exactly `{ "mode": "adc" }` or `{ "mode": "file", "path": "/root/provisioning/gcp-archiver.json" }`. |

File authentication requires a canonical absolute path to protected service-account
JSON. Provision the file independently on both data hosts. Product source copies
it into the application directory as `archive-credential.json`, root-owned with
group 10001 and mode `0640`, and mounts it read-only at
`/etc/siemcore/archive-credential.json` in application/archiver containers.
The source adds archive environment settings and a dedicated
`docker-compose.archive.yml`; conflicting retry settings/credentials are rejected.
ADC requires usable workload identity in the actual runtime, not merely on the host.
No LLM secret field is introduced by this schema.

### `application.allocation_observer` (Observer only)

Requires schema 3, topology `pod`, pod_role `witness`, and an explicit unique
`updater_instance_id`. The exact object fields are:

| Field | Value |
| --- | --- |
| `protocol` | `observer-bootstrap-v1` |
| `drain_config` | Canonical absolute path to protected native Observer drain/service configuration JSON. |
| `update_config` | Canonical absolute path to protected native Observer update-adapter configuration JSON. |

These referenced files use the SiemCore native schemas; they are not arbitrary
user-defined JSON. Obtain them from SiemCore provisioning. Update configuration
must retain `qualified: false`. Source bootstrap is intended to verify enrollment,
TLS and authenticated quorum health without creating an active assignment or
activating updater lifecycle readiness. Clean-install qualification is pending.
Unlike legacy schema 2 witness bootstrap, this explicit new path does not require
`redis_auth`. It does not require application, database, LLM or archive credentials.

## Invocation and stored files

From the extracted kit, supply the shared enrollment flags above and the matching
role/input choice. For example, after setting the shell variables to approved values:

```sh
sudo ./install.sh --clean \
  --greenfield-input /root/provisioning/pod-a.json \
  --server-type pod-active --pod-id "$POD_ID" --node-id 1 \
  --instance-id "$UPDATER_INSTANCE_ID" \
  --parent-url "$PARENT_RELAY_URL" --parent-id "$PARENT_INSTANCE_ID" \
  --customer-id "$CUSTOMER_ID" --customer-name "$CUSTOMER_NAME" \
  --license-key "$ENROLLMENT_CREDENTIAL" --signing-key "$SIGNING_PUBLIC_KEY" \
  --self-update-channel stable
```

| Installation | Replace input / role flags with |
| --- | --- |
| Normal | `--greenfield-input /root/provisioning/normal.json --server-type normal` (omit POD/node flags) |
| POD B | `--greenfield-input /root/provisioning/pod-b.json --server-type pod-stby --pod-id "$POD_ID" --node-id 2` |
| Observer | `--greenfield-input /root/provisioning/observer.json --server-type pod-observer --pod-id "$POD_ID" --node-id witness` |

| Host path | Content |
| --- | --- |
| `/etc/siemcore/greenfield.json` | Application input plus local machine identity, created private (`0600`). |
| `/etc/siemcore/greenfield-release.json` | Signed first-release receipt, created private (`0600`). |
| `/etc/siemcore/updater-bootstrap.json` | Input fingerprint for idempotent retry. |
| `/etc/siemcore-cascade-updater/config.yaml` | Enrollment, signing pin, product and updater configuration. |
| `/var/lib/siemcore-greenfield/secrets.json` | Generated Normal bootstrap secrets, retained for retries. |

Keep original provisioning inputs private. Retries must reuse the same inputs;
changed input is rejected rather than silently reinitializing. After installation,
verify actual product/updater versions, restart, cascade heartbeat and role-specific
health. POD processing must wait for authority/readiness; updater enrollment alone
is not application or POD readiness.

## Internal artifact handoff (not an administrator parameter)

The outer verified bootstrap hook supplies `SIEMCORE_BOOTSTRAP_ARTIFACT` to the
signed product entrypoint. It points to the hook's private verified archive;
Observer intake independently verifies that archive against the signed first-release
receipt before retaining it. Administrators do not set this variable or infer a
path from the updater cache. This supports configurable download-cache directories.

Full three-clean-VM POD bootstrap remains unqualified; A/B independent-database
integration is still a product release gate. The parameter reference and isolated
Observer update evidence do not establish complete POD installation readiness.

## Validate before installing

From a kit containing this source update, run:

```sh
sudo python3 ./greenfield-bootstrap.py --validate-input /root/provisioning/pod-a.json
```

This performs read-only envelope validation (private file/parents, size, schema,
identity and release receipt encoding); it never creates users or starts services.
It does not verify a downloaded artifact signature, test cloud access, or prove
application readiness. The installer performs this check before host changes.
The signed product executor validates detailed application configuration.

### Schema-4 scoped quorum identity mapping — not enabled

For the independent-data POD path, node `1` uses updater quorum certificate CN
`updater-1`, node `2` uses `updater-2`, and node `witness` uses
`updater-observer`. These are read-only, POD-scoped certificate principals, not
registered updater machine IDs. Controller CNs are `1` and `2`; Observer authority
uses a separate privileged credential. Bootstrap API certificate pins remain a
separate binding. No public package includes private credentials.

This mapping is reserved for the matching qualified schema-4 kit. Existing
schema2/3 input and credential handling is unchanged. The current kit still
rejects schema4; accepting this mapping does not enable delivery or activation.
